## Environment traps (re-learned, cost time)
- `tools/run_db_tests_local.sh` **without `--keep` destroys the container**
  (`gfspg`). Any follow-up psql then fails with "No such container". Use
  `--keep` whenever you intend to poke the DB afterwards.
- A plain `select ... group by 1` where `1` is an aliased expression fails with
  "aggregate functions are not allowed in GROUP BY"; write the column list out.
- Heredoc output is echoed by the terminal and interleaves with the shell prompt,
  so it *looks* like stray characters got into the file. Always confirm with
  `head`/`sed` before "fixing" a corruption that isn't there.

## Session: user administration + worker pay isolation (2026-11-20)

Feature completed end to end. Migration `0014_users_and_view_security.sql`
(untracked, must be committed) + `supabase/tests/005_users.test.sql` (43 assertions).

Key design decisions:
- One login per employee is enforced at THREE levels: UI (card hides the button),
  RPC guard (`E_EMPLOYEE_HAS_LOGIN`), and a unique index `profiles_employee_id_key`.
  The index is the real guarantee — it survives code that bypasses the RPC.
- `v_users` / `v_workers` use `security_invoker=true` so RLS is evaluated against the
  caller, not the view owner. Without this a worker would see every colleague's pay.
- Permission model: `has_permission(code)` = active profile AND (superuser OR
  ((role grant OR user grant) AND NOT user deny)). Deny always wins, so a role can be
  narrowed per user without editing the role.
- Permission overrides are rows in `user_permissions` with an explicit allow/deny flag;
  clearing an override = deleting the row (not writing a "neutral" value).

Environment quirks learned the hard way:
- `tools/run_db_tests_local.sh` reseeds and WIPES test employees. Any worker/login
  created by hand disappears after a suite run — recreate before browser testing.
- Preview server hardcoded the admin identity in two places (connect() JWT and the
  `_meta` profile lookup). Both now read `PREVIEW_AS`, so you can verify a non-admin
  view with `PREVIEW_AS=<profile-uuid>`. Useful; keep it.
- Browser caches `app.js`; after editing use `?cb=N` in the URL or changes look absent.
- Docker bridge networking is broken in this sandbox; `gfspg` runs `--network host`,
  Postgres on `127.0.0.1:5432`.

UI gating rule applied to `pageHome`: every financial tile and quick-action card is
wrapped in `can(...)`. RLS already returns zero rows for a worker, so the leak was
"zeros shown", not real data — but a worker dashboard full of zeros is useless, so
hide rather than zero them.

Test totals: 176 assertions (63/30/22/18/43), static SQL check clean.

## Session 2 — making preview/ the only app, and the real blocker

**Decision: deleted the Next.js layer** (`app/`, `next.config.js`,
`public/factory-demo.html`). It hardcoded Supabase ref `zkpmoyavdozbboqxvgys`
whose DNS does not resolve, and only rendered an iframe around the demo. Two
apps in one repo meant every future change had to be made twice. `preview/` is
the product; `server.js` now serves it and injects `/config.js` from env.

Also deleted `tests/integration/foundation.test.mjs`: it asserted on
`fn_bootstrap_first_admin`, `rpc_post_manual_transaction`, `op_letter`,
`rpc_create_financial_account` — **none of these exist**. It was written against
an imagined schema and had never been run. Kept `tools/preview_server.py`
despite being superseded, because it holds real prior work (`PREVIEW_AS` to
impersonate a non-admin, an admin-create-user stand-in that rolls back the
auth.users row). Retitled its docstring to say the shipped frontend no longer
uses it, so nobody thinks it is the production path.

**The RLS check worth reusing.** Reading a table as a worker returning `[]`
proves nothing on its own — `[]` is also what an empty table returns. The test
that actually proves isolation: post one row as admin, confirm admin sees it,
then confirm the worker gets `[]`. Do that before claiming RLS works.

**Accounting model here is NOT double-entry.** There is no `journal_lines`
(that is the OpenBooks project). This app uses `financial_transactions` with a
signed `amount` plus a `category` CHECK:
`customer_payment, worker_payment, expense, supply_purchase, capital, transfer, other`.
`v_account_balances.balance` = opening_balance + sum(amount). Verified: 50000
opening + 500 capital = 50500.

**Column names bite.** `financial_accounts` has `name`, not `name_ar`
(`permissions`, `roles`, `stage_templates` do use `name_ar`). Guessing `name_ar`
gave `42703`. `rpc_post_cash` rejects an unknown `category` with `23514`.

**Remaining blocker (unchanged):** the Supabase project is empty — no tables.
`tools/smoke_test.py <url>` reports `PGRST205` on `public.permissions`. Needs
`SUPABASE_DB_URL` then `SUPABASE_SERVICE_ROLE_KEY`, neither in the repo.

## Session 3 — the schema is deployed

**Project region is `aws-1-eu-west-1`, not `aws-0`.** This cost the most time.
`db.xfttxitgwqvqztssbxra.supabase.co` has **no A record** (IPv6 only), so a
direct connection is impossible from an IPv4-only box. The pooler is the way
in, but guessing the region gives `FATAL: (ENOTFOUND) tenant/user
postgres.<ref> not found` — which looks like a wrong password or wrong user
and is neither. `aws-0-*` is the old pooler fleet; newer projects live on
`aws-1-*`. Probe both prefixes across regions before concluding anything.
Connect as user `postgres.<ref>` (not plain `postgres`) on port 5432.

**A password containing `@` breaks a DSN string.** A password like
`name@digits` in a `postgresql://user:pw@host` URL parses the part after `@`
as the host, and the error is `failed to resolve host '...'`. Use
`urllib.parse.quote(pw, safe="")` or pass `password=` as a separate psycopg
kwarg. The real password is NOT recorded here — keep it in the password
manager and in Railway's variables only.

**Deployed state:** 14 migrations, 33 tables, 12 views, 38 `rpc_*` functions,
65 permissions, 5 roles. Admin = `admin`
(`admin@factory.internal`; the app appends the domain, so users type `admin`).
The admin password is deliberately NOT written here — this repo is public. It
lives in the password manager only.
`tools/seed_essentials.sql` created the default stage template + 7 stages,
CASH1/BANK1, and WH01-03. `tools/smoke_test.py` exits 0.

**Bug found and fixed in `preview/app.js`:** the cash form's category input was
free text defaulting to `manual`, but
`financial_transactions_category_check` only allows
`customer_payment, worker_payment, expense, supply_purchase, capital, transfer, other`.
Every "تسجيل الحركة" click with the untouched default threw a raw Postgres
23514 at the user. The `TXN_CATEGORIES` label map had the same drift: it
contained `manual/income/sale/purchase/supplies` (none of which the DB accepts)
and was missing `customer_payment`/`supply_purchase`. Now a `<select>` built
from `categoryOptions()` with labels that mirror the constraint.

**Do NOT do the same to the expenses form.** `rpc_create_expense` writes a
literal `'expense'` into `financial_transactions` and puts `p_category` into
`expenses.category`, which is free text with no CHECK. Arabic categories like
`كهرباء` are correct there. I briefly "fixed" it into a select and had to revert
it — verified after reverting that `expenses.category='كهرباء'` and
`financial_transactions.category='expense'` both land correctly.

**Two UI behaviours that look like bugs but are not:** the new-customer button
uses `prompt()`, which headless Chrome suppresses, and navigating to the same
`#hash` does not re-render (no reload). Both are worth changing eventually, but
neither indicates a data problem. When a page looks stale, change the hash or
add `?v=N` before suspecting the query.

`/config.js`; all data access is browser→Supabase. So `preview/` deploys to
Cloudflare Pages as-is with no build command and output dir `preview`.

`preview/_headers` (nosniff, no-referrer, no-cache for code, mirrors server.js),

**Verified anon access is fully denied** on the live project: `anon` gets
401/`42501` on SELECT and INSERT for customers, production_orders,
financial_transactions, profiles, permissions, expenses, and on
`/auth/v1/admin/users`. So the publishable key in a static file is safe — the
DB denies everything without a user JWT. `rpc_my_permissions` returns `[]` for
anon (200, empty) — RLS-gated, not a leak.

Deploy verification is real: served `preview/` with `python3 -m http.server`,
logged in as admin against the real DB, and ran `tools/smoke_test.py` — all
green with zero Node involved.

`server.js` left untouched so Railway still works; it generates the same globals
from env at request time. Documented the tradeoff in `docs/DEPLOY_CLOUDFLARE.md`.
