## Session: user administration + worker pay isolation (2026-11-20)

Feature completed end to end. Migration `0014_users_and_view_security.sql`
(untracked, must be committed) + `supabase/tests/005_users.test.sql` (43 assertions).

Key design decisions:
- One login per employee is enforced at THREE levels: UI (card hides the button),
  RPC guard (`E_EMPLOYEE_HAS_LOGIN`), and a unique index `profiles_employee_id_key`.
  The index is the real guarantee — it survives code that bypasses the RPC.
- `v_users` / `v_workers` use `security_invoker=true` so RLS is evaluated against the
  caller, not the view owner. Without this a worker would see every colleague's pay.
- Permission model: `has_permission(code)` = active profile AND (superuser OR
  ((role grant OR user grant) AND NOT user deny)). Deny always wins, so a role can be
  narrowed per user without editing the role.
- Permission overrides are rows in `user_permissions` with an explicit allow/deny flag;
  clearing an override = deleting the row (not writing a "neutral" value).

  view with `PREVIEW_AS=<profile-uuid>`. Useful; keep it.
- Browser caches `app.js`; after editing use `?cb=N` in the URL or changes look absent.

## Session 3 — the schema is deployed

**Project region is `aws-1-eu-west-1`, not `aws-0`.** This cost the most time.
`db.xfttxitgwqvqztssbxra.supabase.co` has **no A record** (IPv6 only), so a
direct connection is impossible from an IPv4-only box. The pooler is the way
in, but guessing the region gives `FATAL: (ENOTFOUND) tenant/user
postgres.<ref> not found` — which looks like a wrong password or wrong user
and is neither. `aws-0-*` is the old pooler fleet; newer projects live on
`aws-1-*`. Probe both prefixes across regions before concluding anything.
Connect as user `postgres.<ref>` (not plain `postgres`) on port 5432.

**A password containing `@` breaks a DSN string.** A password like
`name@digits` in a `postgresql://user:pw@host` URL parses the part after `@`
as the host, and the error is `failed to resolve host '...'`. Use
`urllib.parse.quote(pw, safe="")` or pass `password=` as a separate psycopg
kwarg. The real password is NOT recorded here — keep it in the password
manager and in Railway's variables only.

## Cloudflare deploy failure — root cause (resolved)

Symptom: `Failed: error occurred while running deploy command` on every deploy.

Root cause: Cloudflare Pages detects `package.json` and runs `npm run build`
automatically. The repo had **no** `build` script → instant failure. Two
compounding problems:

1. `package-lock.json` still listed Next.js / React / supabase-js from an
   earlier Next-based version of the project, while `package.json` declared
   **no** dependencies. A lockfile that disagrees with `package.json` is what
   makes `npm ci` refuse on CI. Locally it survived because npm 12 tolerates
   it — so it did NOT reproduce locally. Always test with a fresh clone.
2. `node_modules/` on disk was leftover Next.js; regenerating the lock while
   it existed re-inherited all 30 packages. Had to `rm -rf node_modules`
   before `npm install --package-lock-only` to get a clean 1-package lock.

Fix: `build` script → `node tools/build-static.js` (copies `preview/` → `dist/`,
hard-fails if index.html/app.js/db.js/config.js/sw.js missing). Lock regenerated.
Cloudflare config is now: build `npm run build`, output `dist`.

Verification that actually proves it: fresh `git clone` → `npm ci` → `npm run
build` → serve `dist/` → `tools/smoke_test.py` 13/13 PASS.

Lesson: local `npm ci` success means nothing when node_modules is present.
The clone-and-build simulation is the only reliable check.

## CI/CD: what actually works (learned 2026-11-21)

**Secret names are not guessable — read them from a failed run, don't guess.**
The DB password secret is `DATABASE_PASSWORD`. `SUPABASE_DB_URL` also exists but
holds an **https URL, not a connection string**, so any code that feeds it to
psycopg must check the `postgres://` prefix first.

**The password contains `@` and other URL metacharacters.** Inserting it raw into
`postgresql://postgres:<pw>@host` moves the host boundary and every candidate
resolves a garbage hostname like `02-2015@db.<ref>.supabase.co`. Always
`urllib.parse.quote(password, safe="")`.

**`db.<ref>.supabase.co` is IPv6-only and does not resolve** on GitHub runners or
in this sandbox. The IPv4 route is the pooler, and the user must be written as
`postgres.<ref>` (not `postgres`). Working host:
`aws-1-eu-west-1.pooler.supabase.com:5432` — note `aws-1-eu-west-1`, which is not
the project's own region, so trying several regions is worth it.

**The Cloudflare token is the real blocker.** It verifies as `active` (53 chars)
but `/accounts` returns an empty list, so it carries no account-level permission
and every Pages call 403s with `code 10000 Authentication error`. This is NOT an
account-id problem: no account id can help a token that reaches zero accounts.
A token needs `Account → Cloudflare Pages → Edit`. Do not burn more time deriving
account ids — that was a dead end.

**`garment-factory.pages.dev` is live but stale** (serves `sw.js` v1 while the
repo is at v6, app.js 158KB vs 240KB). It was published by something other than
the GitHub workflow — most likely the Cloudflare dashboard or the separate
`Workers Builds: garment-factory-system` integration, which also fails with the
same authentication error.

**Never let a skipped publish look like success.** Gating the deploy steps on a
permission probe and letting the job pass turned a broken token into a green run
that shipped nothing. The workflow now fails explicitly when a token exists but
cannot reach Pages.

**`workflow_dispatch` only works from the default branch** — dispatching a
workflow that exists only on a feature branch returns 404. Merge to `main` first,
then dispatch.

**Squash-merging a PR rewrites history**, so the old branch no longer rebases;
cherry-pick the new commits onto a fresh branch off `main` instead.

**The static SQL check now validates insert column names** against the declared
table columns. That class of bug (0015-0017 wrote `label_ar`, the table declares
`name_ar`) used to reach the real database and fail there.
# 2026-11-20 — add-user failure + stage templates rebuild

## Root cause of "انت مش متصل بالسيرفر" when adding a user
Two independent faults, both in `admin-create-user`:

1. **The Edge Function was never deployed.** `POST`/`OPTIONS` to
   `/functions/v1/admin-create-user` return `404 NOT_FOUND`.
2. **Even deployed, its CORS was wrong.** It advertised only
   `authorization, content-type`, but `preview/db.js` also sends `apikey`.
   A preflight that does not echo a requested header fails, and the browser
   reports the failure as a network `TypeError` — *not* as an HTTP error.

That second point is why the symptom lied: `humanError()` sees `TypeError`
with no `status` and prints "السرفر مش راد". A missing function and a broken
CORS config are both indistinguishable from a dead server in the browser.
Diagnostic that actually separates them: compare `OPTIONS` on the function
against a known-good endpoint (`/auth/v1/token` returns 200 with
`access-control-allow-headers: authorization,content-type,apikey`).

## Why no SQL-only fallback exists
Creating a login requires a row in `auth.users` with a hashed password.
That schema belongs to Supabase Auth; writing to it directly is unsupported
and would break token issuance. So user creation *must* go through either the
Admin API or an Edge Function holding the service-role key. There is no way to
make add-user work from the browser alone.

## Deployment blocker
This sandbox has no `SUPABASE_ACCESS_TOKEN`, no service-role key and no
`DATABASE_PASSWORD` (all empty). The function therefore cannot be deployed
from here. `.github/workflows/deploy-functions.yml` is ready and needs only
`SUPABASE_ACCESS_TOKEN` added as a repo secret; then run it manually.

## Stage templates screen
The reference app (`/orders/templates`) is a tab per template plus one card per
stage with up/down/delete and dependencies as **tick boxes**. Ours was a
read-only table per template plus a comma-separated text field for
`depends_on` — the user had to type internal stage codes by hand.

Rebuilt to match. Three traps worth remembering:
- `formDialog` takes `{ key, label }`, **not** `{ name, label }`. Passing
  `name` silently yields `undefined` for the field.
- `rpc_save_stage_template` **deletes and re-inserts every stage**. So
  "rename template" must resend the existing stages or it wipes them.
- The same RPC accepts `is_final` / `is_operations`, and `is_final` is what
  makes goods "ready for delivery" (0005_rpc.sql:369). An editor that omits
  these flags silently clears them on every save.
